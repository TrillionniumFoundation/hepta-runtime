# Five binary handler call plans

This private HIA owner consumes successful results from the five qualified typed parameter owners and preserves the original caller preconditions and request construction in binary.rs. It does not replace filesystem bodies or implement authority. Only an owning runtime caller may supply its private phases and actual installed-configuration replies.

The input is a 48-byte HBPLQ001 header followed by one complete HBPRR001 typed success frame and then the exact optional HRCFGM01 configuration reply. Header u64 fields are phase at 8, observation pool requested Boolean at 16, typed frame extent at 24, feedback extent at 32, and zero at 40. Phase 0 starts a call with no feedback. Phase 1 resumes the inode caller's original read-path check. Phase 2 resumes the original RPC configured-root lookup. Phase 1 is valid only for inode patch. A successful phase-1 reply is the empty 32-byte permission result. Both reply phases preserve the complete original error text; a successful phase-2 reply contains the original raw root bytes. The caller owns phase order and completion identity.

All typed header, reserved words, optional bits, applicable fields, full string extents and UTF-8 are validated. Empty strings, None versus Some(empty), None versus Some(0), all u64 values and NUL within Rust strings retain their original distinctions. No extra path, base64, version, transaction identity or root policy is imposed here. The exact retained UTF-8 function is reused from the installed config owner.

The output is a 64-byte HBPLR001 header followed by complete payload. Fields are status at 8, kind at 16, next phase at 24, operation at 32, write/audit-needed flag at 40, actual observation mode at 48, and payload byte count at 56. Status 1 carries exact original business error text. Status 2 carries an actual HRCFGQ01 operation-8 or operation-9 request, including zero user/port flags and exact host/path bytes. Status 3 carries the exact compact sorted JSON object sent by the original handler after root selection. Its operation values 1..7 are info/read/write/upload_chunk/upload_commit/upload_abort/inode_patch. Only info/read use the observation flag; all three write handlers require the original downstream audit before transport.

Inode acknowledgement precedes its initial read-path check. The apply field checks occur only after that successful check. Every caller then performs its original RPC root lookup. Binary write's encoded byte bound, upload identity and action-dependent requirements, read-limit clamping, exact optional JSON nulls, and inode offset default retain their original order and values. String serialization preserves UTF-8, original JSON control escapes and complete unsigned decimal numbers. Remote operation bodies and their additional validations remain separate.

The return is the complete published output extent. Output shorter than 64 returns 0xfffffffe. Invalid framing returns 0xffffffff before mutating output or workspace. A valid call needs 512 workspace bytes; insufficient workspace or output returns 0xffffffd0 with the 32-byte HGRWS002 request (kind 1 or 2, exact required capacity, zero reserved word), leaving the remaining output tail unchanged. Sizing is a pure first pass over immutable input; publication occurs only after the full extent fits. Workspace is private scratch and output tails beyond publication remain unchanged. The return extent is bounded below 0xffff0000.

This qualification composes the actual Map, five typed owners, caller plan, and admitted installed-config ELF in private test transports. It compares the unchanged original caller bodies and post-admission argument boundaries. Actual remote filesystem bodies, audit implementation, SSH session, public gateway and asynchronous scheduling remain outside this stage.
