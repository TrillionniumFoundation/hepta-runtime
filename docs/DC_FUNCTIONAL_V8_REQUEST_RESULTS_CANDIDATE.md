# V8 bounded original request-result candidate

This isolated source candidate adds `request_status` and `request_result`. It preserves all 58 frozen V7 tool definitions and the original 50 V4 definitions exactly. V4–V7 contracts remain unchanged. This is a reviewed bounded result-recovery slice, not full Desktop Commander replacement or universal `get_tool_result` equivalence.

Only successful validated `host_list`, `host_health` and `effective_config` DTO results are eligible. Their outputs contain selected capability metadata or a fixed redacted SSH health observation; request parameters, credentials, arbitrary stdout, errors and unexpected DTO shapes are not cached. History/status/result lookup are never recursively cached. Other tool calls retain existing path-free dispatch metadata; their caller-visible exact result IDs remain a gap.

The private `request-results` sibling ledger uses descriptor-relative nofollow access, owned 0700 directories and owned single-link regular 0600 files, atomic staging and fsync. It caps records at 128 per owner and 512 globally, original retained JSON at 64 KiB, record files at 96 KiB and pages at 16384 original bytes. Stale result records are removed on a later eligible admission once their audit IDs expire. Each request has an unknown result intent before dispatch. Crashes and unavailable results never trigger replay.

The exact stored boundary is native serialized `CallToolResult` after the server-generated request identity marker, before retention acknowledgement and transport-version normalization. Pages return base64, an independent byte offset and full immutable-snapshot SHA256. The maximal stored acknowledgement is included in the 64 KiB retention eligibility budget. Overflow preserves the full original live DTO and same request ID, records only overflow metadata, and refuses result recovery. Effective configuration and lookup methods preview maximal final acknowledgement size against their existing 256 KiB and 64 KiB response caps; an over-cap read-only response becomes an explicit bounded same-ID refusal without claiming the original was retained. Existing search/batch/process envelopes receive no added metadata.

Ownership comes only from the verified private HTTP credential or the existing random stdio session. Same HTTP credential can recover eligible results after reconnect/restart when the complete loaded runtime-policy binding is unchanged. Any configuration change conservatively revokes previous result access. Different credentials and caller-selected owner fields are refused. This is not authenticated ChatGPT user, conversation or caller isolation, and does not establish PTY/job caller ownership. Stdio remains native-session-only.

The unchanged six-field V7 audit record remains the dispatch-status authority. A temporary owned read pin is established under the audit lock before lookup admission and held through snapshot generation; it prevents self-eviction and concurrent quota eviction. Pins do not change crashed unknown dispatches into accepted/running status. Metadata does not prove transport delivery or business completion.

After result or audit completion persistence fails, eligible responses preserve original content and the same ID and state `durability_unknown`; they never invite automatic retry. Lost responses before a caller receives an exact ID cannot be unambiguously correlated solely from history. True early-return asynchronous start and request cancellation are remaining work.

Acceptance uses a disposable native HTTP process and a fixed private local SSH-command emulator. It is local-origin protocol/fault evidence, not real SSH, six-machine replacement or model-origin business evidence. Existing installed services, tokens, rollback artifacts and Desktop Commander are untouched. Integration, release rebuild, combined six-machine acceptance and real model business qualification remain separate gates.
