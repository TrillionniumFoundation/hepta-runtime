# X230 A40 revision 02: bounded throughput and output recovery

## Accepted checkpoint

A40 revision 02 retains the A38 archive and opt-in file-observation changes
and fixes inherited-output-pipe recovery without shortening the original
per-stream natural completion budgets. The exact source passed X230 format,
strict Clippy, all-feature tests and release qualification. A serial follow-up
then used the same qualified executable for archive, native recovery, six-host
controller recovery, fixed ABBA, sustained-load and capacity checks.

The accepted implementation keeps the file pool opt-in and retains **8 global
sessions, 2 per host, 8 queued and 16 admitted requests**. No installed runtime
or controller service was replaced or restarted. All source, executables,
profiles and fixtures were isolated under the X230 optimization workspace.
The main host supplied an existing forwarded SSH agent and ran only owned
launchers/fixtures; no private keys were copied.

This checkpoint contains two product-source changes relative to A38 commit
`6dc54f2173c40bf84bb879c917583a16dc39d52b`: `jobs.rs` and its output-durability
tests. A39 and A40 revision 01 remain rejected attempts, with their exact
source deltas, failures and diagnostic results preserved. Their successful
tests or soak runs are not used to qualify A40 revision 02.

## Same-executable six-host ABBA

The four rounds used off/on/on/off order, the same executable, and six existing
immutable synthetic job stdout files on ai395, mac, main, pocket4, rog and
x230. Each round had 96 measured requests at C1, C4 and C8, with a balanced
host/tool mix. The tools were `file_info` and `binary_read`; files were only
44–48 bytes. These results concern observation overhead and latency, not bulk
transfer bandwidth or arbitrary application-job throughput.

All **1,248 call rows** passed: **1,152 measured, 48 warmup and 48 negative**.
The negative cases required the exact stale-version and outside-root errors.
Successful reads were checked against original bytes, size, hash, version,
cursor and EOF. No failed request was automatically retried.

The weighted rate is the sum of successful measured calls divided by the sum
of measured wall times in the two rounds for each mode. Two observations per
mode provide descriptive evidence, not a confidence interval.

| Concurrency | Pool off, calls/s | Pool on, calls/s | Change |
| --- | ---: | ---: | ---: |
| 1 | 2.2042 | 3.8263 | +73.59% |
| 4 | 7.8651 | 15.1861 | +93.08% |
| 8 | 11.6602 | 21.6879 | +86.00% |

At C8, off-round p95 was 881.87/863.65 ms and on-round p95 was
461.78/426.57 ms. C1 off-round p95 varied from 538.62 to 887.77 ms, so the
original order and all samples remain visible; stationarity is not assumed.

## Resource tradeoff

Waited `RUSAGE_CHILDREN` deltas were captured after each original controller
exited. They cover complete local controller rounds and the local descendants
reaped by those controllers, including startup, warmup, measured requests,
negative cases and shutdown. Remote-host CPU and the external sampler's CPU
are outside this scope. Controller-only CPU would omit the relevant movement
of SSH work into the pooled controller.

| Resource | Pool off, two rounds | Pool on, two rounds |
| --- | ---: | ---: |
| Waited local process-tree CPU | 120.725519 s | 68.427654 s |
| Per-round sampled tree RSS peaks | 80,064 / 80,068 KiB | 120,332 / 113,188 KiB |
| Per-round sampled controller RSS peaks | 16,460 / 16,388 KiB | 17,328 / 17,284 KiB |

CPU decreased **43.32%** for the fixed complete rounds. Sampled tree RSS
increased from about 78.2 MiB to 117.5/110.5 MiB. This measured memory cost
supports an explicit opt-in choice for memory-constrained deployments.

Fourteen distinct FD permission errors were retained across the four final
resource samples; earlier accumulated snapshots repeat some of them. The
sampler is not atomic or exhaustive, and FD observations are incomplete.
Sampled peaks are not proven process or descriptor limits. All four original
controllers exited 0 after stdin EOF, with no unmatched responses, reader
errors or surviving descendants among the identities actually observed.
This is not a universal absence-of-processes proof.

## Multi-host coordination and recovery

The final [six-running-job recovery report](evidence/x230-a40/six-running-recovery-report.json)
records six fresh original jobs, one on each configured host. The canary
observed those originals running, killed only its owned original controller,
restarted the isolated controller and issued six same-key lookups. It checked
the original job identities, independent running state, one-execution markers,
full outputs and terminal witnesses. The six original jobs continued; no
workload was relaunched to manufacture recovery.

The whole harness took 19.02 seconds, including preparation, launch, deliberate
hold/release and verification. This is not a general recovery-time objective.
The experiment kills a controller while remote supervisors remain alive; it
is not a host reboot or power-loss experiment.

The [independent recovery analysis](evidence/x230-a40/recovery-independent-analysis.json)
recomputes the retained request/output/exit/witness bytes and checks all six
original identities, same-key replies and controller waits. The registry state
and ELF files are excluded from the archive; the offline analysis checks their
retained receipt bindings rather than claiming a new read of those files.

The final [native inherited-pipe report](evidence/x230-a40/native-inherited-pipe-report.json)
passed six cases: natural output EOF, staggered stdout/stderr EOF, and retained
pipe timeout, each on X230 and Mac. Naturally staggered output remained a
complete success. Forced cleanup retained Unknown/incomplete semantics and
used the original unreaped leader's group identity. The harness retained
native wire requests/responses, original outputs, receipts and witness checks.
It did not signal a reconstructed remote PID to rescue a failed product case.

The eight [source-bound prequalification cases](evidence/x230-a40/prequalification-report.json)
also exercised ignored TERM, immediate TERM-induced EOF, read exceptions with
no EOF, and the two rejected-source counterexamples. Their Rust counterparts

Direct signal-before-reap event traces come from those source-bound fixtures.
The native canaries independently verify original group metadata, signal
receipts and output/terminal originals. Their optional native cancellation

prequalification fixtures and the qualified test suite.

## Persistence and output-recovery behavior

The [recovery and persistence design](X230_A40_RECOVERY_DESIGN_20261025.md)
describes the source-level protocol and its limits. The important changes are:

- After a normal leader exit, retain the original child unreaped until any
  needed original-group signal has been attempted. Linux uses non-reaping
  `waitid`; Mac uses the original process's kqueue exit event.
- Preserve stdout's original two-second wait and then stderr's two-second
  wait, with an overall four-second drain/join waiting budget. This is not a
  four-second bound on scheduling, blocked I/O, synchronization or publication.
- Natural advancement requires actual EOF, an ended reader thread and a
  completion timestamp within its deadline. A read exception can end a thread
  while a descendant remains alive and must not skip group cleanup.
- Forced drain, including TERM that immediately produces EOF, remains
  `effect_outcome=unknown`, `exit_code=125`, output incomplete and automatic
  retry disabled. A leader exit of zero does not prove a terminated descendant
  completed its effects.
- Reader-start failure after workload creation retains the existing original
  group cleanup, original child wait and joins for every reader actually
  started. Failure receipts preserve the initial error and cleanup outcomes.
- Complete output is distinguished from synchronized output. A matching
  terminal witness binds job ID, nonce and the exact exit-receipt bytes after
  their preceding file/directory synchronization barriers returned. It does not
  certify arbitrary external effects or prove survival of a real power cut.

fresh native-owner fixtures, each containing 64 true `host_list` audit records.
It also retained all 256 seed calls, 32 warmups and 40 before/after validation
queries. Usage, history and archive results were checked against complete

The archive implementation is substantially shared by A35 and the final
candidate. One ABBA block does not establish statistical significance or

## Current boundary and follow-up design

This is the validated checkpoint for the current hardware and measured workload.
It does not establish an absolute maximum across all possible implementations.
The next changes would need separate workload or failure evidence:

- Large files, writes, transfers, WAN variation and mixed application jobs are
  outside the 44–48-byte observation comparison.
- Abrupt controller exits can leave old socket roots. Safe automatic reclamation
  needs durable provenance plus live original-process custody or a verified
  handoff; a stored PID or pathname cannot supply signal authority.
- Blocked kernel I/O, supervisor death, escaped process groups, reboot and real
  power loss require separate custody and reconciliation protocols and tests.
- Arbitrary external exactly-once effects require application-specific
  idempotency or transactional commit/query support. Unknown remains a valid
  result, and this runtime does not blindly replay uncertain effects.

The local X230 qualification is not a claim of GitHub Actions success. The
predecessor A38 [workflow run](https://github.com/TrillionniumFoundation/hepta-runtime/actions/runs/40154841387)
reported failure with `runner_id=0`, empty runner name and no job steps; the
available metadata did not establish its cause. Current PR checks are an
independent gate and must be read on the current commit. This remains a draft
source/evidence checkpoint rather than a production rollout.

The [reproduction guide](../tools/x230/a40/README.md) identifies the exact tools,
fixed experiment paths, input bindings, failed-attempt harnesses and analysis
limits. The [publication manifest](evidence/x230-a40/publication-manifest.json)
binds the submitted product source and evidence files.
