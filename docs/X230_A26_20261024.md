## Narrow waiting for an empty argv observation

The [D4 record](X230_A25_D4_20261024.md) captured two live-child observations with
a pidfd, matching UID and executable identity, and empty argv. Those events
motivated a narrowly bounded readiness wait. They did not establish exec versus
exit as the cause, or identify the cause of earlier generic proof failures.

A26 enters this wait only for the original registered `OwnedChild`, with a
pidfd, a nonterminal child, and an initial identity whose UID and executable
device/inode match the expected SSH executable while argv is empty. The same
child remains in the ownership ledger. The wait uses the caller's original
absolute deadline and checks request cancellation and pool stop; it never
refreshes the budget or starts another child.

Every repeated identity observation and terminal probe uses the same child lock
as owner wait/reap paths. Re-observation requires the original birth identity,
UID, executable identity, and either still-empty argv or the exact expected
argv. A contradictory nonempty argv or changed identity is refused immediately.
Read failures leave readiness without retry: A26 adds no `ENOENT`, `EACCES`, or
other errno exception. Cancellation and deadline are checked again before
accepting an otherwise matching observation.

Empty snapshots do not fill the child's identity `OnceLock`. A matching live
identity can establish readiness; an observed terminal child follows the
existing owned-child terminal handling without treating empty argv as live
authority. Failures retain the existing stop, reap, and ledger-release path.
The child and its admission permits remain owned until actual cleanup.

Sibling tests cover exact matching, serialized reaping, identity contradictions,
read errors, cancellation, the original deadline, a late matching observation,
and a contradictory observation followed by exit. These are bounded correctness
checks, not an attribution of the historical incidents.

## Two validation-drain boundaries

A25 already drained complete-file validation workers inside `Core::shutdown()`
before successful socket/root unlinking. An early supervisor-lock or uncertain
child-cleanup error could return before reaching that drain. A26 retains the
original in-Core drain and adds a second owner boundary after `Core::shutdown()`
returns, whether its result is `Ok` or `Err`.

After stopping admission, the owner waits for
`Workers::finish_shutdown(cleanup)`. This awaits actual closure completion
before applying `cleanup.and(drained)`, preserving the original cleanup error
and the owner's existing actor/error precedence. Successful cleanup keeps its
drain-before-unlink ordering; an early cleanup error also encounters the final
worker-lifetime barrier before owner teardown proceeds.

The isolated fixtures exercise real early cleanup errors with two blocked
validation closures whose async callers have been aborted. The final barrier
stays pending until both closures finish. Queued and newly submitted validation
calls observe stop without starting file reads, and the original cleanup error
is retained. These fixtures exercise actual Core errors and the production
finalizer; they do not simulate a successful SIGKILL cleanup.

The barrier cannot forcibly interrupt blocked kernel I/O. A validation closure
that remains blocked can therefore delay orderly shutdown. SIGKILL can prevent
the owner from running either drain entirely. No automatic reclamation of an
older controller's socket residue is included; PID values, directory names,
and artifact age do not establish ownership of those objects.

## Inherited authority and persistence rules

A26 retains A25's process-wide shared limit of eight unfinished
archive-history/usage query closures. Each observation pool separately limits
complete-file validation to two unfinished closures. Their permits follow real
closure lifetimes, including after caller cancellation. These are specific work
limits, not a bound on all runtime threads or waiters.

Archive metadata queries retain the single three-second acceptance deadline
set at API entry. Admission, blocking-pool queueing, locking, and query work
consume that budget. Workers refuse access when already expired at entry, and
the final check rejects successful results accepted after the deadline.
Already-started I/O may finish later. Existing owner/session scope checks,
archive identities, complete-file hashes, and owner-side authority rechecks
remain required.

The A20 execution identity, durable output, and terminal-witness contract remains
the [execution durability and recovery contract](RUNTIME_DURABILITY_BOUNDARIES.md).
The candidate changes observation readiness and validation ownership; it does
not establish additional guarantees for remote effects, target reboot, or
physical power loss.
