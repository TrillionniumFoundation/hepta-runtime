# Local browser capture through the existing native owner

`deploy/hepta_browser_capture.py` is a finite worker for an explicitly bounded
workload: observe SHA-bound local resources through a new private Chrome, save
two HAR 1.2 captures at the same loopback origin, and read those saved captures
with the existing REA MCP tools. Launch it with `process_start`; the original
native job owns admission, host binding, idempotency, output, cancellation and
recovery. No new daemon or durable task registry is introduced.

The worker imports the private Chrome lifecycle in
`deploy/dc_compat/chromium_pdf.py`. PDF rendering uses that same lifecycle. It
creates its own profile and loopback CDP connection, closes its browser, and
cleans only its original process group on failure. It cannot discover or attach a
user browser, accept a user profile, select arbitrary Chrome flags or replay
arbitrary CDP commands. No Chrome installation or service change is performed.

The shared Linux lifecycle is its child's exclusive reaper. It requires default
SIGCHLD handling, visible Linux proc group membership, and non-reaping
`waitid(..., WNOWAIT)` support. A finite, owned `/bin/true` preflight confirms
real child custody before Chrome starts, including configurations where
automatic reaping is invisible to Python's handler query. Neither this module
nor dc_compat installs a shared arbitrary-child reaper. Callers must preserve
that exclusive-reaping contract for the lifetime of the call.

An exited leader stays waitable until cleanup, reserving its original PID and
process-group identity. Cleanup signals only that original group, checks within
a bounded interval that it has no live members, then performs the sole final
child wait. Zombies are not live members. Foreign reaping, loss of the exit
witness, a failed group signal, or a termination timeout produces an
`unconfirmed` failure and prevents a success receipt. Descendants that move to
another session are outside this original-group guarantee. The helper does not
claim a general descendant supervisor.

Capture installs cancellation handling only in its main thread. Child creation
and final cleanup defer the first cancellation; browser work between them stays
interruptible. A signal arriving during connection close cannot skip group
cleanup and reaping, and connection-close errors still enter group cleanup.
Cleanup uncertainty takes precedence over a pending cancellation. PDF calls,
including their existing worker-thread path, install no signal handlers.

## Exact input and execution scope

The entry page is generated by the worker. Its fixed JavaScript fetches the
declared resource paths in order, including repeated paths. Resource HTML and
JavaScript are response data: they are **not executed as an application**.
This is a real browser resource-observation adapter, not general web automation,
Electron application execution, browser-state replay or full upstream REA
parity.

The CLI takes an absolute manifest path, its required SHA-256, and a new output
directory that must be a direct child of the manifest's directory:

```text
python3 deploy/hepta_browser_capture.py \
  --manifest /owned/case/fixture.json \
  --expected-sha256 MANIFEST_SHA256 \
  --output-directory /owned/case/capture
```

Run that executable/argv with an explicit native `process_start` host, cwd,
idempotency key, timeout and memory budget. The worker is an optional checkout
or packaged helper, not a newly installed MCP service. A helper bundle needs
`hepta_browser_capture.py`, `dc_compat/__init__.py`,
`dc_compat/chromium_capture.py`, and the existing `dc_compat/chromium_pdf.py`,
plus the already installed Python websocket package and system Google Chrome.
The PDF module keeps its existing path and dependencies; no new shared module
has been introduced into its deployment import chain.

A manifest has this form; both SHA values must be the actual file digests:

```json
{
  "schema": "hepta.rea.local-browser-capture.v1",
  "resources": [
    {
      "url_path": "/data.txt",
      "mime_type": "text/plain; charset=utf-8",
      "before": {"file": "before.txt", "sha256": "ACTUAL_BEFORE_SHA256"},
      "after": {"file": "after.txt", "sha256": "ACTUAL_AFTER_SHA256"}
    }
  ],
  "requests": ["/data.txt", "/data.txt"],
  "timeout_seconds": 30
}
```

Unknown fields, duplicate JSON members, absolute resource paths, parent
traversal and symlink traversal refuse. Every resource is read once from an
admitted descriptor, fully hashed, and retained as bounded bytes before Chrome
starts. Source metadata is checked across that read. Omitting `after` reuses the
declared `before` input. A fixture may explicitly select `delivery: "truncated"`
to exercise incomplete-response observations, or a bounded `delay_ms` for
original-job cancellation qualification. These settings do not enable an
arbitrary HTTP server or external URL input.

## Network claims

The source server binds an ephemeral `127.0.0.1` port and serves only this
manifest's captured bytes and the fixed entry page. Both capture phases use
that **same origin**. The page's CDP Fetch gate admits only its generated page
and declared exact resource URLs.

A fixed internal bootstrap marks each new document with its capture generation.
Both readiness and the completed harness result must match the current phase;
the old document's same URL and resolved promise cannot satisfy the next phase.
This does not change the URL, query string or saved fixture response bytes.

A second call-owned loopback server supplies a negative control. A direct
control request first proves that this server is listening. The generated page
then attempts a simple cross-origin request, which must be observed and denied
by the page gate. Successful capture requires the second server's browser
request count to remain zero. A DNS failure is not used as this evidence.

This is a **page/session request gate**, not process-level network isolation.
The receipt explicitly reports `process_level_network_isolation=false`.
Chrome's existing background-network disabling flags do not prove that every
browser process or system component is network isolated. The adapter executes
only its fixed authored script and does not expose arbitrary page code to this
limited boundary.

The Fetch gate remains installed until the owned browser is closed, but this
qualification does not claim WebSocket blocking or interception of new popup
targets. The receipt explicitly sets `websocket_blocking_qualified=false`,
`popup_navigation_blocking_qualified=false`, `input_page_dom_inspected=false`
and `arbitrary_page_execution_supported=false`. No input resource is evaluated
or inserted into a DOM; this restricted producer must not be reused as a
sandbox for executing arbitrary page code.

## Budgets and saved-body semantics

| Resource | Limit |
| --- | --- |
| Manifest | 64 KiB; unique JSON members |
| Resources | 16 |
| Each source version | 64 KiB |
| Total captured source versions | 2 MiB |
| Declared requests per phase | 32; repeated paths preserved |
| Observed requests per phase | 64 |
| Received CDP messages for the call | 2,048; 8 MiB total |
| Individual received CDP message | 256 KiB, checked before JSON parsing |
| Decoded CDP body representation | 64 KiB each; 2 MiB total for both phases |
| Final encoded HAR | 4 MiB per phase |
| Final encoded receipt | 64 KiB |
| CDP operation timeout | 1–60 seconds; native job timeout remains the outer bound |

The websocket library receives a message before its byte limit is checked.
These are observation/serialization bounds, not a sealed Chrome heap limit.
Use the existing native job's memory and timeout controls as the process owner.

Each entry distinguishes these states in its `_hepta` metadata:

- `complete`: CDP returned a nonempty text representation.
- `empty`: CDP returned an explicitly recorded zero-length body.
- `base64`: CDP returned an encoded body; HAR preserves the exact base64 text and
  `encoding: "base64"`.
- `missing`: no body representation was obtained; `content.text` is omitted,
  with a bounded reason and actual network-completion status.

SHA-256 values bind the recorded text representation and its decoded
representation where present. The receipt separately binds the original local
source files. CDP headers and bodies are observations, not raw HTTP wire bytes,
and charset conversion or browser decoding must not be relabeled as wire
equivalence. `every_response_body_recorded` remains false when any body is
missing. A CDP message/body budget failure fails the worker rather than silently
turning into an ordinary missing body.

## Publication and recovery

The worker finishes and closes its private browser before publishing
`before.har`, `after.har` and `capture-receipt.json`. The output directory must
be new. Each file is written to a private exclusive staging inode, file-synced,
published with a create-only link, and parent-directory-synced. Existing files
are never replaced. The final receipt is published last; success is printed
only after all required syncs succeed.

An error after visible publication is an unconfirmed outcome. Partial output
does not become a successful capture receipt. Preserve the original native
request and idempotency key, observe its status and output, and do not use a
fresh key to replay an uncertain capture. Cancellation handles SIGTERM through
the shared private-browser cleanup and stops the call's own loopback servers.
Abrupt SIGKILL cannot run Python cleanup; terminal-owner observation and
explicit reconciliation of that job's private scratch remain necessary.

For this first qualification, the worker and controller run on the **same
Linux host**. On different hosts, a worker path is not a controller path. No
automatic cross-host artifact transport or shared filesystem is asserted.

## Actual MCP qualification

`tests/rea_browser_capture_tests.py` covers source identity and refusal,
request/message/body/final-encoding bounds, distinct empty/base64/missing body
semantics, exact page denial, create-only publication, parent-fsync uncertainty,
the shared lifecycle's cancellation/ownership-loss paths, an actual finite
subprocess whose leader exits before its descendant, all-method sentinel
counting, and preservation of a venv Python invocation path. No Chrome is
started by this suite.

The opt-in real driver is `tests/rea_browser_external.py`. In an explicitly
scheduled browser window, run it with the candidate runtime and this helper:

```text
python3 tests/rea_browser_external.py \
  --runtime /absolute/candidate/hepta-runtime \
  --capture-helper /absolute/checkout/deploy/hepta_browser_capture.py \
  --python /usr/bin/python3 \
  --workspace /absolute/new-owned-qualification-directory \
  --allow-owned-browser --allow-local-ssh
```

It captures through actual MCP `process_start`, proves same-key reuse and only
one browser-start record, checks both phases at the same origin, then reads,
compares and replays through the shipped REA tools. After capture closes, it
rebinds the old source/probe ports with live counted sentinels, proves those
listeners reachable, restarts the MCP controller, and requires saved-response
replay to produce exact recorded bytes with zero accepted connections and zero
HTTP requests reaching either sentinel. Requests are counted before method
dispatch, including unsupported methods. Positive-control connection/request
counts are reset before replay. This observation covers these two known owned
origins, and does not assert host-wide network isolation. It also cancels a slow fixture through the original job, confirms the
terminal state, checks that the job's original private process group has no live
members and its profile is removed, and
proves reusing the cancelled key does not launch another browser.

The selected Python keeps its absolute invocation path so a venv symlink retains
its environment semantics. The driver separately records and rechecks its
resolved target path and SHA-256. This pins the interpreter executable, not all
installed Python packages.

A separate fixture retains its manifest and original request identities while
one source file is deliberately changed. The actual native job must fail before
any browser-start record or capture receipt, and the same idempotency key must
reuse that failed job with unchanged output.

The driver records runtime/helper source identities, original requests, job
admissions, terminal logs, HAR identities, actual MCP results and
`qualification.json`. A passing receipt is required before claiming the live
adapter qualified. Its existence in source or an independent CDP oracle is not
such a receipt. The existing offline HAR contract remains unchanged: response
replay reads saved representation bytes and performs no browser execution or
network replay.
